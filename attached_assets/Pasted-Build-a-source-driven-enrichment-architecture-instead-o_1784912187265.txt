Build a source-driven enrichment architecture instead of a generic HTML scraper. Treat every scholarship provider as a trusted data source with its own extraction strategy while exposing a single normalized scholarship model to the rest of the application. The goal is that no component outside the scraper layer knows or cares how the information was obtained. Every scraper must ultimately produce the same complete scholarship object containing title, description, rich content, eligibility, benefits, deadlines, funding details, cover image, gallery images, application links, organization, country, level, tags, and metadata.

Build the pipeline as a sequence of independent stages. The first stage discovers opportunities from listing pages and returns only lightweight metadata such as title, source, URLs, publication date, and category. The second stage removes duplicates in memory. The third stage removes records that already exist in the database. Only after these filters should enrichment begin, ensuring that expensive requests are never performed for discarded items.

Build an enrichment engine that delegates work to specialized extractors. The engine should inspect the domain and automatically choose the best extraction strategy. Instead of forcing every website through one parser, the engine should support multiple strategies that share one interface. Static HTML websites should use a fast Cheerio-based extractor. Websites exposing JSON-LD should use a structured data extractor. React, Next.js, Nuxt, and Vue applications should first search for embedded hydration state before attempting HTML parsing. Websites exposing REST or GraphQL endpoints should consume those APIs directly. Only websites that cannot be parsed using any of these methods should fall back to a browser renderer such as Playwright. Browser rendering should be treated as the last resort rather than the default.

Build every extractor to follow a waterfall strategy. Attempt to retrieve structured data first because it is usually the cleanest and most complete representation. If structured data is unavailable, inspect embedded application state such as `__NEXT_DATA__`, `__NUXT__`, hydration payloads, or serialized JSON objects. If those are absent, perform semantic HTML extraction using meaningful elements such as article bodies, headings, figures, metadata, and schema attributes. Only if all previous attempts fail should the extractor launch a browser, wait for hydration, and capture the rendered page. This layered strategy minimizes cost while maximizing accuracy.

Build a normalization layer immediately after extraction. Every source expresses scholarship information differently, but the application should never receive inconsistent structures. Normalize dates into a single format, convert currencies into structured values, standardize education levels, countries, organization names, application URLs, and funding information, remove duplicated paragraphs, decode HTML entities, sanitize markup, compress whitespace, and produce clean Markdown or sanitized HTML for storage. Rich content should preserve headings, lists, tables, quotations, and links so that opportunities remain visually appealing when displayed.

Build a content quality pipeline that scores every extracted scholarship before it is accepted. Reject placeholder pages, loading skeletons, cookie banners, navigation menus, empty pages, login screens, and application portals masquerading as content. Measure extracted text length, paragraph count, heading count, image count, metadata completeness, and content density. If quality falls below a defined threshold, automatically retry using the next available extraction strategy before marking the opportunity as incomplete.

Build a media extraction system that prioritizes meaningful images rather than every image found on the page. Prefer Open Graph images, Twitter Card images, schema.org images, article hero images, and large content images before considering generic `<img>` elements. Ignore logos, icons, avatars, advertisements, tracking pixels, placeholders, SVG decorations, and navigation graphics. Store one cover image and a curated gallery while preserving image dimensions, captions, alt text, and source URLs.

Build semantic section extraction rather than storing one large block of text. Identify sections such as Overview, Eligibility, Benefits, Funding, Requirements, Required Documents, Application Process, Selection Criteria, Timeline, Deadlines, Contact Information, Frequently Asked Questions, and Additional Notes. Store these as structured fields while also generating a polished full description for presentation. This enables future filtering, AI search, and personalized recommendations without repeatedly parsing raw content.

Build domain adapters instead of hardcoded conditions scattered throughout the codebase. Every supported website should have its own isolated module containing listing discovery, detail extraction, normalization rules, quality validation, and optional browser automation. Register these adapters through a dispatcher so adding a new scholarship source becomes a configuration task rather than a modification of the entire pipeline.

Build intelligent caching for every network request. Cache downloaded pages, structured data responses, media metadata, robots rules, and discovered endpoints using URL hashes and expiration policies. Cache successful enrichments for a configurable period and avoid repeatedly requesting unchanged opportunities. This dramatically reduces bandwidth, improves performance, and protects source websites.

Build observability into every stage. Record which extraction strategy succeeded, how long it took, whether a browser was required, the quality score achieved, which structured fields were populated, how many images were extracted, and why any fallback occurred. Every scholarship should have a complete enrichment trace that makes failures immediately understandable without reproducing the scrape.

Build the architecture so that the database stores a normalized, presentation-ready scholarship rather than raw scraped HTML. The frontend should never perform extraction or cleanup. When the API returns an opportunity, it should already contain polished content, structured sections, optimized media, normalized metadata, and consistent formatting regardless of whether the source was a university website, government portal, international organization, or private foundation.

Build the system with extensibility as the primary design principle. New scholarship sources should require only a new adapter that implements the shared extraction contract. The orchestration pipeline, normalization layer, quality engine, caching system, storage model, search index, and frontend should remain unchanged. This separation of concerns produces a scalable architecture capable of supporting hundreds of scholarship providers while maintaining consistent, high-quality content throughout the platform.

# Build Scholr as a Source-Driven Editorial Platform, Not a Scraper

Build Scholr around the philosophy that scraping is only the first step in producing a trustworthy opportunity. The platform must never display raw HTML or simply mirror another website. Instead, every opportunity should pass through an intelligent editorial pipeline that transforms scattered information into a structured, searchable, visually appealing, and verified opportunity page. Every scholarship, internship, fellowship, grant, job, conference, competition, exchange program, or research opportunity should feel as though it was created specifically for Scholr while always preserving attribution to the original source.

Build the ingestion pipeline as multiple independent stages rather than a single scraper. The first stage discovers opportunities from trusted sources. The second stage performs duplicate detection using URLs, titles, organizations, deadlines, and semantic similarity to avoid storing duplicate opportunities. The third stage enriches every opportunity by extracting the detail page and collecting all available information. The fourth stage converts the extracted content into structured sections such as overview, eligibility, benefits, required documents, funding, application process, deadlines, locations, contact information, important notes, and frequently asked questions. The fifth stage extracts metadata including academic level, country, institution, organization, opportunity type, funding type, study field, language requirements, application period, duration, and other searchable attributes. The sixth stage verifies links, validates deadlines, discovers attachments, detects PDFs, and checks whether the application portal is still active. The seventh stage assigns a quality score and confidence score before sending the opportunity to the editorial workspace.

Build an adaptive extraction engine instead of relying on a single HTML parser. The extraction engine should intelligently try multiple strategies until meaningful content is found. It should begin with structured metadata such as JSON-LD, Open Graph tags, Schema.org, and embedded application data. If these are unavailable, it should inspect framework hydration data such as Nuxt, Next.js, Astro, or other client-side state objects. If that fails, it should extract semantic HTML from article elements, headings, paragraphs, lists, tables, and metadata. If the page is rendered dynamically, it should automatically escalate to a headless browser capable of executing JavaScript before attempting extraction again. Every extraction stage should record which strategy succeeded, how long it took, and the confidence of the extracted information.

Build comprehensive image discovery into the enrichment process. Build rich opportunity pages instead of long blocks of HTML. Every published opportunity should contain structured sections that can be independently rendered, searched, summarized, translated, and edited.
